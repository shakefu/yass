HOWTORUN — the yass CLI
=======================

Requirements
------------

  Go 1.24 or newer, and network access on the first build so the module cache
  can fetch the single dependency (gopkg.in/yaml.v3 v3.0.1). Nothing else: no
  configuration file, no environment variable, no per-repository setup.

  To install a released binary without Go, see the README's Install section:
  an installer script, Homebrew, and `yass update` for keeping it current.

Build, from a clean checkout
---------------------------

  cd cli
  go build -o yass .

  That writes a single static binary named `yass` into cli/. Move or link it
  anywhere on PATH; it reads nothing beside the file tree it is pointed at.

  To install it on PATH instead:

  cd cli
  go build -o "$(go env GOPATH)/bin/yass" .

Run
---

  yass [-C DIR] [--version] [--help] [SUBCOMMAND [ARGS...]]

    overview                       orient a reader in this program and this project
    root [--format FORMAT] [PATH]  report the project root governing PATH
    query [--raw] TARGET...        emit each addressed document, references resolved
    list [--filter GLOB] [--format FORMAT] [PATH...]
                                   index the documents of a tree
    find [--slot SLOT] [--format FORMAT] PATTERN
                                   search obligation prose and design content
    refs [--in] [--out] [--format FORMAT] TARGET
                                   report the reference edges of one document
    validate [--format FORMAT] [PATH...]
                                   check files against the yass language definition
    lint [--format FORMAT] [PATH...]
                                   report graph hygiene of the project
    docs [NAME]                    index the carried documents, or write one
    update [--format FORMAT]       replace this binary with the newest release

  Global options are written before the subcommand token; a subcommand's own
  options are written after it. A TARGET is `path@Name::SLOT`, in which `path@`
  and `::SLOT` are each optional.

  `--format json` makes a record-writing subcommand write each record as one
  compact JSON object per line instead of TAB-separated text; `--format text`
  is the default. Standard error stays text.

  An invocation naming no subcommand runs `overview`, which writes the block a
  reader needs on first contact: what this program is, what project the starting
  directory sits in, the notation a spec file uses, the commands that read a
  spec set, and the reading paths through the carried documents for eliciting,
  writing, changing, or implementing a spec. Running `yass` with no arguments
  is the intended way in.

  Exit statuses: 0 ok, 1 findings, 2 usage, 3 unresolved, 4 no-root,
  5 environment.

Examples, run from this directory
---------------------------------

  ./yass
  ./yass overview
  ./yass root
  ./yass list
  ./yass list --filter '*@*Command*'
  ./yass list --filter 'root*'       # the file record and its documents (* crosses @)
  ./yass list --filter root          # the file record only
  ./yass query 03-root@RootCommand
  ./yass query --raw 04-query@Resolution
  ./yass query root@ExitPolicy
  ./yass find 'byte-identical'
  ./yass find --slot ERROR 'exit with the usage status'
  ./yass refs 01-locate@FileSet
  ./yass list --format json
  ./yass find --format=json 'byte-identical'
  ./yass validate
  ./yass lint
  ./yass lint --format json
  ./yass docs
  ./yass docs authoring

  The repository holds two projects: this directory (the CLI) and the directory
  above it (the yass language definition). Each has its own root.yass.yaml, so
  `yass` run from either sees only that project's files.

Carried documents
-----------------

  `yass docs` indexes the documents that are authoritative for the yass
  language and for writing specs in it, each with the task that earns reading
  it, and `yass docs NAME` writes one whole. They are embedded in the binary,
  so they travel with it and are served from any directory, with or without a
  project root.

  They are read in paths, every document in order, and `yass overview` lists
  the paths: the write path (authoring, documents, obligations, references,
  coverage), the elicit path (brainstorming, then the write path), and the
  language (language, then the write path), and the implement path
  (implementing). Each fits in 200 lines, so a read
  through `head -200` loses nothing; the language definition is longer and
  opens with a line stating its length.

  Read a path when your task matches it. Implementing code against a spec set
  that already exists takes the implement path alone: the notation summary in
  `yass overview` is all a spec file takes to read.

  The embedded copies are built from the checkout by `script/sync-docs`; run it
  after editing any of those files. `go test ./...` fails when a copy has
  drifted from its source.

Test
----

  script/test        (from the repository root)

  It runs the installer tests (script/test-install), then fails on any file
  `gofmt -l` lists, and runs `go vet ./...`, `go test ./...`, and `go build`.
  The built binary then runs script/check-specs, which validates and lints
  both of the repository's spec projects and fails on any validation error or
  on a lint advisory its policy marks as failing.
  For the Go checks alone, run from this directory:

  test -z "$(gofmt -l .)" && go vet ./... && go test ./... && go build -o /dev/null .
