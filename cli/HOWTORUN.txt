HOWTORUN — the yass CLI
=======================

Requirements
------------

  Go 1.24 or newer, and network access on the first build so the module cache
  can fetch the single dependency (gopkg.in/yaml.v3 v3.0.1). Nothing else: no
  configuration file, no environment variable, no per-repository setup.

  To install a released binary without Go, see the README's Install section:
  an installer script, Homebrew, and `yass update` for keeping it current.

Build, from a clean checkout
---------------------------

  cd cli
  go build -o yass .

  That writes a single self-contained binary named `yass` into cli/. Release
  archives are built with CGO_ENABLED=0, as script/build does. Move or link it
  anywhere on PATH; it reads nothing beside the file tree it is pointed at.

  To install it on PATH instead:

  cd cli
  go build -o "$(go env GOPATH)/bin/yass" .

Run
---

  yass [-C DIR] [--version] [--help] [SUBCOMMAND [ARGS...]]

    overview                       orient a reader in this program and this project
    root [--format FORMAT] [PATH]  report the project root governing PATH
    query [--raw] TARGET...        emit each addressed document, references resolved
    list [--filter GLOB] [--format FORMAT] [PATH...]
                                   index the documents of a tree
    find [--slot SLOT] [--format FORMAT] PATTERN
                                   search obligation prose and design content
    refs [--in] [--out] [--format FORMAT] TARGET
                                   report the reference edges of one document
    validate [--format FORMAT] [PATH...]
                                   check files against the yass language definition
    lint [--format FORMAT] [PATH...]
                                   report graph hygiene of the project
    cite [--format FORMAT] TARGET...
                                   write the citation line of each addressed obligation
    citations [--missing | --coverage] [--tests GLOB] [--format FORMAT] [PATH...]
                                   check test citations, or report what they leave uncovered
    docs [NAME]                    index the carried documents, or write one
    explain [ID]                   index lint rule ids, or explain one
    update [--format FORMAT]       replace this binary with the newest release

  Global options are written before the subcommand token; a subcommand's own
  options are written after it. A TARGET is `path@Name::SLOT`, in which `path@`
  and `::SLOT` are each optional. `yass cite` also takes a TARGET ending in
  `[n]`, the 1-based number of an obligation in its slot, with an optional
  `#stamp` after it.

  `--format json` makes a record-writing subcommand write each record as one
  compact JSON object per line instead of TAB-separated text; `--format text`
  is the default. Standard error stays text.

  An invocation naming no subcommand runs `overview`, which writes the block a
  reader needs on first contact: what this program is, what project the starting
  directory sits in, the notation a spec file uses, the commands that read a
  spec set, and the reading paths through the carried documents for eliciting,
  writing, changing, or implementing a spec. Running `yass` with no arguments
  is the intended way in.

  Exit statuses: 0 ok, 1 findings, 2 usage, 3 unresolved, 4 no-root,
  5 environment.

Examples, run from this directory
---------------------------------

  ./yass
  ./yass overview
  ./yass root
  ./yass list
  ./yass list --filter '*@*Command*'
  ./yass list --filter 'root*'       # the file record and its documents (* crosses @)
  ./yass list --filter root          # the file record only
  ./yass query 03-root@RootCommand
  ./yass query --raw 04-query@Resolution
  ./yass query root@ExitPolicy
  ./yass find 'byte-identical'
  ./yass find --slot ERROR 'request-failure catalogue'
  ./yass refs 01-locate@FileSet
  ./yass list --format json
  ./yass find --format=json 'byte-identical'
  ./yass validate
  ./yass lint
  ./yass lint --format json
  ./yass cite 04-query@Query
  ./yass cite 04-query@Resolution::RETURN
  ./yass citations
  ./yass citations --missing
  ./yass citations --coverage
  ./yass docs
  ./yass docs authoring
  ./yass explain
  ./yass explain yass.lint.obligation_shape

  The repository holds two projects: this directory (the CLI) and the directory
  above it (the yass language definition). Each has its own root.yass.yaml, so
  `yass` run from either sees only that project's files. A PATH operand anchors
  root discovery, so `./yass validate <path>` checks the tree that path names
  from any directory; a PATH in another project, a nested one included, exits 4.

Carried documents
-----------------

  `yass docs` indexes the documents that are authoritative for the yass
  language and for writing specs in it, each with the task that earns reading
  it, and `yass docs NAME` writes one whole. They are embedded in the binary,
  so they travel with it and are served from any directory, with or without a
  project root.

  They are read in paths, every document in order, and `yass overview` lists
  the paths: the write path (authoring, documents, obligations, references,
  coverage), the elicit path (brainstorming, then the write path), and the
  language (language, then the write path), and the implement path
  (implementing). Each fits in 200 lines, so a read
  through `head -200` loses nothing; the language definition is longer and
  opens with a line stating its length.

  Read a path when your task matches it. Implementing code against a spec set
  that already exists takes the implement path alone: the notation summary in
  `yass overview` is all a spec file takes to read.

  The embedded copies are built from the checkout by `script/sync-docs`; run it
  after editing any of those files. `go test ./...` fails when a copy has
  drifted from its source.

Lint rule documentation
-----------------------

  `yass explain` indexes the lint rule ids in a fixed order, one record per id.
  `yass explain ID` writes what that rule detects, why it exists, how to resolve
  a finding, and bad/good YAML examples. IDs match byte-for-byte; prefixes,
  abbreviations, and other casing do not resolve. An unknown ID reports
  yass.explain.unknown on standard error, leaves standard output empty, and
  exits 3. Use the index to find an ID.

  The explanations are built into the program. Neither form reads the file
  tree or needs a project root; neither accepts --format. They cover lint
  rules, not validation errors or request failures.

Citations
---------

  A citation is the comment a test carries naming the one obligation it covers:

    // yass: path@Name::SLOT[n]#stamp

  `n` counts the obligations of the slot that carry a keyword, from 1, and the
  stamp is eight characters derived from the obligation's wording. The marker
  is recognized wherever it stands on a line, in any comment syntax, and only
  the token after it is read. A token holding neither `@` nor `::` is not a
  citation, so a key spelled like the marker in a configuration file binds
  nothing.

  `yass cite TARGET` writes the citation line of each obligation a spec, a
  slot, or a file holds that a citation can name, so one is pasted rather than
  counted. A slot a spec declares twice and a document outside the project's
  spec files are passed by. It also takes TARGET as a citation's token with its
  stamp, and then resolves the obligation the stamp names wherever it has moved
  in the slot; a stamp no obligation carries, as after a rewording, exits 3.

  `yass citations` reads every citation in the project's test files and writes
  one diagnostic per citation that is malformed (yass.citation.syntax), names
  no obligation (yass.citation.unresolved), or carries a stamp the obligation
  at its number does not (yass.citation.stale, a warning), exiting 1. A
  citation resolves only against this project's spec files: one naming a file
  above the root or in a nested project is unresolved. A file is named as a
  test when its basename holds `test`, `tests`, `spec`, or `specs` as a whole
  part, in any casing: x_test.go, test_x.py, x.test.ts, XTest.java. A spec file
  is never named as a test. `--tests GLOB` replaces that rule, matching the
  whole root-relative path, and a PATH narrows the files read, a file PATH
  being read whatever its name. The tree is walked as the spec files are, so
  nothing is skipped for being hidden, ignored, or vendored.

  `yass citations --missing` lists, in the form `yass cite` writes, every MUST
  and SHOULD obligation no citation covers. `yass citations --coverage` counts
  per spec the obligations that MUST and that SHOULD, with how many of each are
  covered, then the project's totals on a line whose REF is `-`. A MAY is a
  permission: it can be cited, but --missing never lists it and --coverage
  never counts it. Both reports check nothing and exit 0, unless a spec file
  fails to parse: that is reported on standard error and ends with 1.

Test
----

  script/test        (from the repository root)

  It runs the installer tests (script/test-install), then fails on any file
  `gofmt -l` lists, and runs `go vet ./...`, `go test ./...`, and `go build`.
  The built binary then runs the script tests (script/test-check-specs and
  script/test-pre-commit-hook) and script/check-specs, which validates, lints,
  and checks the citations of both of the repository's spec projects, and fails
  on any validation error or on a lint advisory or citation finding its policy
  marks as failing.
  For the Go checks alone, run from this directory:

  test -z "$(gofmt -l .)" && go vet ./... && go test ./... && go build -o /dev/null .
